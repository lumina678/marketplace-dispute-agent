# MVP 产品与系统规格

## 1. 产品定位

本系统服务于二手交易平台的争议审核员。它根据交易快照、双方主张、案件证据和交易发生时有效的平台规则，生成可追溯、可审核、可申诉、后续可安全执行的处置建议。

系统不是法院、仲裁机构或律师，也不允许大模型直接作出不可逆的最终裁决。所有 MVP 案件必须经过人工审核；退款、退货、放款仅在后续阶段的模拟账户中执行。

## 2. MVP 范围

### 2.1 唯一争议类型

- `DESCRIPTION_MISMATCH`：二手笔记本电脑的关键配置、功能状态或维修历史与发布页、商品照片或聊天承诺不一致。
- 首批重点字段：内存容量、硬盘容量、处理器/显卡型号、设备/主板序列号、功能状态、维修历史。

### 2.2 用户和角色

| 角色 | 能力 |
| --- | --- |
| 买方 | 提交争议、陈述、证据和申诉；回答补问 |
| 卖方 | 提交抗辩、证据和申诉；回答补问 |
| 审核员 | 查看完整证据链；要求补证；批准、修改或拒绝建议 |
| 系统编排器 | 锁定快照、控制状态、暂停恢复、限制预算、记录事件 |
| 分析 Agent | 在授权数据范围内生成结构化分析，不改变订单或资金 |
| Decision Guard | 用确定性规则检查证据、政策、金额、权限和幂等性 |

### 2.3 地域、语言与金额

- 演示平台：`demo-marketplace`。
- 语言：简体中文。
- 币种：人民币，金额统一保存为整数分 `amount_minor`，禁止使用浮点数。
- 时间：存储为带时区的 ISO 8601；平台规则生效边界使用 `Asia/Shanghai`。

## 3. 案件输入

每个案件至少需要：

- 交易 ID、支付时间、实付金额、买卖双方 ID。
- 创建争议时锁定的商品页和图片哈希。
- 创建争议时锁定的相关聊天快照。
- 买方至少一项结构化主张。
- 卖方陈述可在初次调查后补充。
- 物流节点和签收时间（如存在）。
- 证据原文件元数据、内容哈希、提交人、提交时间和来源。
- 以交易 `paid_at` 为选版基准的有效平台政策。

文件内容后续保存在本地证据目录；数据库和 Agent 材料仅保存受控路径、哈希、提取结果和引用，不复制不可控的原始文本作为系统指令。

## 4. 系统输出

一次可提交审核的调查必须产出：

1. 买方主张与卖方抗辩的结构化清单。
2. 统一时间线。
3. 每项证据的来源、完整性、相关性和证明力评估。
4. “主张—证据—规则”引用关系。
5. 未解决问题及必要的补问。
6. 支持、不支持或证据不足的逐项事实认定建议。
7. 退款、退货、部分退款或驳回等处置建议。
8. 金额与运费承担方式。
9. 人工审核原因、Decision Guard 结果和审计信息。
10. 面向审核员的详细说明与面向用户的简明说明草稿。

任何事实若没有 `evidence_ids`，只能标记为 `alleged`、`disputed` 或 `unknown`，不得写入 `established_facts`。

## 5. 允许的建议结果

- `RETURN_AND_FULL_REFUND`：退货并全额退款。
- `PARTIAL_REFUND`：双方明确同意或规则明确允许的部分退款。
- `REJECT_CLAIM`：证据不足或不构成描述不符。
- `REQUEST_MORE_EVIDENCE`：关键事实仍可通过合理补证解决。
- `RELEASE_FUNDS`：争议不成立且满足放款条件。
- `ESCALATE_TO_HUMAN`：超出自动分析或建议权限。

MVP 中即使 Guard 通过，结果也只能进入 `HUMAN_REVIEW`，不能绕过人工审核。

## 6. 强制人工处理条件

至少存在以下任一情况时，必须标记 `requires_human_review=true`：

- 设备或主板序列号冲突，且存在调包或篡改指控。
- 任一方提出欺诈、伪造证据、非法来源或人身安全问题。
- 证据真实性无法通过当前工具确认。
- 建议退款金额超过政策版本的自动建议金额阈值。
- 政策版本缺失、时间区间重叠或没有适用规则。
- 关键事实仅由模型从低质量图片、模糊文本或单方陈述推断。
- 新证据会推翻已执行结果或需要人工追偿。

## 7. 调查循环和补问限制

- 每个案件最多进行 3 轮外部补问；超过后转人工。
- 同一问题不得在没有新理由时重复发送。
- 问题必须关联 `claim_id`、缺失事实和可接受的证据类型。
- 每一轮恢复都创建新的 `case_run_id`，不得覆盖旧分析。
- Agent 单次失败允许确定性重试；达到预算或次数限制后暂停并转人工。

## 8. 权限与安全边界

- 分析 Agent 只允许调用查询工具和创建处置草稿。
- Agent 不得修改原始证据、商品快照、聊天记录、规则版本或交易金额。
- 创建退款、退货、放款等动作必须经过 Guard 和人工审批。
- 写操作必须使用 `case_id + action_type + decision_version` 生成幂等键。
- 所有工具调用记录调用方、参数摘要、结果摘要、耗时和错误类型。
- 证据中的提示、脚本或操作指令一律视为不可信内容。

## 9. 明确不在 MVP 中的内容

- 真实支付、真实物流或真实平台账号连接。
- 法律意见、法定责任认定或司法裁判。
- 假货、空包、运输损坏、缺件等其他争议类型。
- 通用图片取证、深度伪造检测或硬件法证。
- 全自动最终裁决、自动封禁或信用处罚。
- 多币种、多语言、多法域和复杂税务。
- 四个 Agent 多数投票。

## 10. 端到端验收场景

演示案件必须覆盖：

1. 卖家发布“16GB 内存、功能正常、无维修”的二手笔记本。
2. 买家主张实物只有 8GB，且主板序列号与商品照片不一致。
3. 卖家主张发货时为 16GB，怀疑买家更换硬件。
4. 系统锁定交易、商品和聊天快照，建立时间线。
5. 系统识别检测报告不足以独立证明交付时状态，并提出定向补问。
6. 新证据进入后恢复案件，重新评估相关主张。
7. 裁决建议逐项引用证据和交易时有效的政策版本。
8. Guard 能拦截无证据事实、错误政策版本或超额退款。
9. 人工审核后才能进入模拟执行。
10. 申诉提交新证据后创建新决定版本，保留原决定和执行记录。

## 11. 前四步完成定义

- MVP 的范围、角色、输入、输出、非目标和安全边界没有歧义。
- 所有合法流转均在状态机中列出；非法跳转默认拒绝。
- 核心案件材料与 Agent 输出有 Draft 2020-12 JSON Schema。
- 至少存在两个政策版本，生效区间不重叠，能够按 `paid_at` 唯一选版。
- 示例案件的事实、证据和政策引用可以被本地脚本校验。
